# Episode Artwork via Replicate

## Problem / Intent
Episodes currently have no generated cover art, and the podcast feed likely uses a static image. Using an image generation model via Replicate would give each episode a unique visual tied to its content, improving the RSS feed presentation and any future web display.

## Constraints
- Must not block or slow the existing pipeline; artwork generation can run as a separate stage or post-merge step
- Generated images should be deterministic enough that re-running produces consistent results for the same episode
- Need to stay within Replicate pricing and rate limits
- Podcast-level artwork is a one-time generation; episode artwork runs per episode
- Image prompt should draw from existing metadata (title, summary) to avoid an extra LLM call

## Proposed Approach
1. Add a new pipeline stage (e.g., `artwork`) after script or merge that calls the Replicate HTTP API
2. Use episode metadata (title, summary) to construct an image prompt — either via template or a lightweight LLM call
3. Store generated images alongside episode assets in `resources/episodes/<episode_id>/`
4. Reference episode artwork in RSS feed `<item><itunes:image>` during publish
5. Add a separate CLI command or flag for generating the main podcast cover art (one-time or on demand)
6. Add `REPLICATE_API_TOKEN` to `.secrets.env` and `--replicate-model` CLI option

## Open Questions
- Which Replicate model to default to (Flux, SDXL, etc.)?
- Should the artwork stage be optional or part of the default pipeline?
- Should the prompt be generated by an LLM call or templated from metadata fields?
- What resolution and aspect ratio for episode art vs podcast cover (RSS recommends 3000x3000)?
- Should failed artwork generation block publishing or just log a warning?

## Notes
- Replicate API docs: https://replicate.com/docs/reference/http
- Could reuse the existing `--run-stage artwork` pattern for isolated runs
- Podcast cover art could also be generated from a curated prompt describing the show's brand
