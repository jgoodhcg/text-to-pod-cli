# Episode Feedback and Model Quality

## Problem / Intent
The podcast is generated locally, published as RSS and audio files in DigitalOcean Spaces, and primarily consumed by the owner through Overcast. RSS clients do not provide reliable completion or satisfaction telemetry, so there is currently no direct signal for whether an episode was enjoyable or which generation choices produced it.

Collect a low-friction owner rating for each episode, optionally capture what worked or failed, and join that feedback to the existing episode, model-selection, and cost records. The resulting data should support production model allocation based on observed episode quality rather than benchmark rankings alone. Anonymous feedback should remain distinguishable from authenticated owner feedback in case another listener submits a response.

## Constraints
- Keep the existing local CLI and Spaces-based publishing architecture; do not require a Droplet, App Platform service, or managed database
- Make the primary response one tap from episode show notes: liked or did not like
- Do not count link previews, crawlers, or podcast-player prefetches as feedback
- Treat owner ratings as the high-confidence signal and keep anonymous ratings separate
- Keep Function and storage costs within DigitalOcean's free or already-paid usage at the expected personal scale
- Never expose Spaces credentials or an owner authentication secret in the static page source
- Preserve individual feedback events as an append-only audit trail; do not mutate a SQLite database stored in Spaces
- Keep free-form comments optional, bounded, and private

## Proposed Architecture
1. During episode generation, create feedback URLs for `like` and `dislike` and include them near the model metadata in the RSS show notes
2. Serve a small static feedback page from the existing public Space or its CDN endpoint; links preselect the episode and rating but require an explicit form submission before recording an event
3. Submit the form over HTTPS to a public DigitalOcean Function with CORS restricted to the feedback-page origin
4. Validate the episode identifier, rating, reason tags, body size, timestamp, and an HMAC signature generated by the CLI; reject unknown fields and malformed or expired submissions
5. Identify the owner using a long-lived random token stored by a one-time setup page in browser local storage; the Function stores only a verifier and classifies requests without a valid token as anonymous
6. Give the Function a dedicated, limited Spaces key and write each accepted response as a uniquely named JSON object under a private `feedback/events/YYYY/MM/DD/` prefix
7. Add a CLI import command that lists unseen event objects, validates their schema, and inserts them idempotently into the local SQLite database using `eventId` as a unique key
8. Join imported feedback to existing episode generation records by `episodeId`; retain every event while treating the latest owner rating as authoritative for analysis
9. Add reporting that compares owner satisfaction with stage models, model combinations, source type, duration, and estimated generation cost
10. Use accumulated feedback as an input to model-selection weights, with a minimum sample threshold and benchmark ranking as a prior until enough episode ratings exist

## Feedback Schema
Required event fields:

- `version`
- `eventId`
- `episodeId`
- `rating`: `like` or `dislike`
- `reviewer`: `owner` or `anonymous`
- `submittedAt`

Optional fields:

- `reasons`: allowlisted values such as `topic`, `accuracy`, `depth`, `script`, `voice`, `length`, or `technical_issue`
- `comment`: bounded free-form text

Model names, stage assignments, rankings, and costs remain in the episode database and are joined during import rather than duplicated into feedback objects.

## Abuse and Reliability Controls
- Record feedback only on `POST`; `GET` requests only render the confirmation page
- Require a signed episode payload so arbitrary episode identifiers cannot create valid records
- Enforce strict schema validation, short field limits, a small total request-body limit, and a honeypot field
- Use unique object keys so concurrent Function invocations cannot overwrite one another
- Keep the feedback prefix private and bucket listing restricted
- Configure a DigitalOcean usage or billing alert as protection against invocation abuse
- Deduplicate imports locally and allow owner rating changes by appending a new event instead of overwriting history

## Delivery Phases
1. Define and version the event schema, signed-link format, owner-token flow, and local database tables
2. Build the static confirmation form and DigitalOcean Function with append-only Spaces writes
3. Add feedback links to generated RSS show notes and verify the flow from Overcast on the owner's phone
4. Add CLI synchronization, local reporting, and owner-versus-anonymous filtering
5. Add feedback-aware model analysis and carefully introduce it into production selection weights

## Open Questions
- Does Overcast's in-app browser preserve local storage across feedback-page visits, or should owner identification use a different low-friction mechanism?
- Should signed feedback links expire, or remain valid for the lifetime of an episode?
- Should a rating initially support only `like` and `dislike`, or include a neutral option?
- What minimum number of owner-rated episodes should be required before feedback can alter model-selection weights?
- Should model attribution use per-stage effects, whole-pipeline combinations, or both once enough samples exist?

## Notes
- At expected volume, one object per event is simpler and safer than downloading, modifying, and replacing a SQLite database in object storage
- If object count eventually becomes inconvenient, imported historical events can be compacted into monthly NDJSON archives without changing the ingestion model
- Plausible analytics is intentionally out of scope for the initial implementation; the append-only feedback data is the source of truth
- DigitalOcean Functions currently includes a monthly free compute allowance that should comfortably cover personal feedback traffic, but pricing should be rechecked during implementation
